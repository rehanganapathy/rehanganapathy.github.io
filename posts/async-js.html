Asynchronous Programming in JavaScript(Node.js)

A couple of years ago, i was interviewing for a backend developer intern role and i remember going blank when asked about the event loop and async patterns in Node.js. Since then, I've made it a point to try and understand concepts before implementing them, here is are a few examples of how asynchronous programming works in Node.js.

1. The Event Loop

Node.js uses a single-threaded event loop built on libuv. This architecture allows it to handle many concurrent operations without creating multiple threads. The event loop processes callbacks in specific phases, and understanding these phases is crucial for predicting when your code executes.

Event Loop Phases

The event loop cycles through six phases in order:

  1. Timers – Executes callbacks scheduled by setTimeout() and setInterval()
  2. Pending callbacks – Executes I/O callbacks deferred from the previous cycle
  3. Idle, prepare – Internal use only
  4. Poll – Retrieves new I/O events and executes I/O callbacks
  5. Check – Executes setImmediate() callbacks
  6. Close callbacks – Executes close event callbacks (e.g., socket.on('close'))

Microtasks vs Macrotasks

Between each phase, Node.js processes the microtask queue. Microtasks include:

  • process.nextTick() callbacks (processed first)
  • Promise callbacks (.then(), .catch(), .finally())
  • queueMicrotask() callbacks

Macrotasks are the callbacks in the event loop phases (timers, I/O, etc.). The key rule: all microtasks are processed before moving to the next macrotask.

console.log('1: sync');

setTimeout(() => console.log('5: timer'), 0);

Promise.resolve().then(() => console.log('3: promise'));

process.nextTick(() => console.log('2: nextTick'));

console.log('4: sync');

// Output:
// 1: sync
// 4: sync
// 2: nextTick
// 3: promise
// 5: timer
Microtask Starvation: If you recursively add microtasks, the event loop can never move to the next phase. This blocks all I/O operations.

setImmediate() vs setTimeout()

The order of execution between setImmediate() and setTimeout(fn, 0) is non-deterministic when called from the main module, because it depends on process performance. However, when called from within an I/O cycle, setImmediate() always executes first because it runs in the check phase, which comes after poll.

// Non-deterministic order
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));

// Inside I/O: setImmediate is always first
const fs = require('fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
  // Always logs: immediate, timeout
});

2. Promises and Async/Await

Promise States

A Promise has three possible states:

  • Pending – Initial state, neither fulfilled nor rejected
  • Fulfilled – Operation completed successfully
  • Rejected – Operation failed

Once settled (fulfilled or rejected), a Promise cannot change state. This immutability is fundamental to Promise behavior.

Promise Chaining

Each .then() returns a new Promise. The value you return becomes the fulfillment value of that new Promise:

Promise.resolve(1)
  .then(x => x + 1)      // returns 2
  .then(x => x * 2)      // returns 4
  .then(x => console.log(x)); // logs 4

If you return a Promise from .then(), the next .then() waits for that Promise to settle:

Promise.resolve(1)
  .then(x => {
    return new Promise(resolve => {
      setTimeout(() => resolve(x + 1), 1000);
    });
  })
  .then(x => console.log(x)); // logs 2 after 1 second

Async/Await

Async/await is syntactic sugar over Promises. An async function always returns a Promise. The await keyword pauses execution until the Promise settles, then returns its value. 

// These are equivalent:

// Promise version
function getData() {
  return fetchUser()
    .then(user => fetchPosts(user.id))
    .then(posts => ({ user, posts }));
}

// Async/await version
async function getData() {
  const user = await fetchUser();
  const posts = await fetchPosts(user.id);
  return { user, posts };
}
Key difference: With async/await, intermediate values (like user) remain in scope, making code more readable and easier to debug.

Error Handling

With Promises, errors are caught with .catch(). With async/await, use try/catch:

// Promise
fetchData()
  .then(data => processData(data))
  .catch(error => handleError(error));

// Async/await
async function run() {
  try {
    const data = await fetchData();
    await processData(data);
  } catch (error) {
    handleError(error);
  }
}
Unhandled Rejections: In Node.js, unhandled Promise rejections currently log a warning but will crash the process in future versions. Always handle rejections.

3. Concurrency Patterns

Sequential vs Parallel

Sequential execution means operations run one after another. Parallel execution means they start simultaneously:

// Sequential: ~600ms total
async function sequential() {
  const user = await fetchUser();      // 200ms
  const posts = await fetchPosts();    // 300ms
  const comments = await fetchComments(); // 100ms
  return { user, posts, comments };
}

// Parallel: ~300ms total (longest operation)
async function parallel() {
  const [user, posts, comments] = await Promise.all([
    fetchUser(),      // All three start
    fetchPosts(),     // at the same time
    fetchComments()
  ]);
  return { user, posts, comments };
}

Promise Combinators

Promise.all(promises)

  • Waits for all Promises to fulfill
  • Returns array of results in the same order
  • Rejects immediately if any Promise rejects

Promise.allSettled(promises)

  • Waits for all Promises to settle (fulfill or reject)
  • Never rejects
  • Returns array of objects: { status: 'fulfilled', value } or { status: 'rejected', reason }

Promise.race(promises)

  • Settles as soon as any Promise settles
  • Takes the state of the first settled Promise

Promise.any(promises)

  • Fulfills when any Promise fulfills
  • Rejects only if all Promises reject
// Robust error handling with allSettled
const results = await Promise.allSettled([
  fetchUser(),
  fetchPosts(),
  fetchComments()
]);

const user = results[0].status === 'fulfilled' 
  ? results[0].value 
  : null;

const posts = results[1].status === 'fulfilled'
  ? results[1].value
  : [];

Limiting Concurrency

Sometimes you need to limit how many operations run simultaneously. This is important when dealing with rate limits or resource constraints:

async function processWithLimit(items, limit, processFn) {
  const results = [];
  const executing = [];
  
  for (const item of items) {
    const promise = processFn(item).then(result => {
      executing.splice(executing.indexOf(promise), 1);
      return result;
    });
    
    results.push(promise);
    executing.push(promise);
    
    if (executing.length >= limit) {
      await Promise.race(executing);
    }
  }
  
  return Promise.all(results);
}

// Process 100 items with max 5 concurrent
await processWithLimit(items, 5, async item => {
  return await fetch(`/api/process/${item.id}`);
});

4. Common Pitfalls

Blocking the Event Loop

The event loop is single-threaded. CPU-intensive synchronous operations block everything:

// ❌ This blocks the entire server
app.get('/compute', (req, res) => {
  let result = 0;
  for (let i = 0; i < 1e9; i++) {
    result += i;
  }
  res.json({ result });
});

// ✅ Move CPU-intensive work to worker threads
const { Worker } = require('worker_threads');

app.get('/compute', async (req, res) => {
  const worker = new Worker('./compute-worker.js');
  
  const result = await new Promise((resolve, reject) => {
    worker.on('message', resolve);
    worker.on('error', reject);
  });
  
  res.json({ result });
});

Missing await

Forgetting await is a common mistake that leads to subtle bugs:

// ❌ Wrong: data is a Promise, not the actual data
async function wrong() {
  const data = fetchData(); // Missing await!
  console.log(data); // Promise {  }
  return data.value; // undefined
}

// ✅ Correct
async function correct() {
  const data = await fetchData();
  console.log(data); // actual data
  return data.value;
}

Error Handling in Loops

Be careful with error handling when processing arrays:

// ❌ One failure stops everything
async function processAll(items) {
  const results = [];
  for (const item of items) {
    results.push(await processItem(item)); // Throws on error
  }
  return results;
}

// ✅ Continue processing even if some fail
async function processAllRobust(items) {
  const promises = items.map(item => 
    processItem(item).catch(err => ({ error: err }))
  );
  return await Promise.all(promises);
}

Race Conditions

Async operations can complete in unexpected orders:

// ❌ Race condition
let latestData = null;

async function fetchLatest(id) {
  const data = await fetch(`/api/data/${id}`);
  latestData = data; // What if an older request finishes last?
}

// ✅ Track request order
let requestCounter = 0;

async function fetchLatest(id) {
  const requestId = ++requestCounter;
  const data = await fetch(`/api/data/${id}`);
  
  if (requestId === requestCounter) {
    latestData = data; // Only use if still the latest
  }
}

5. Production Best Practices

Timeouts

Always set timeouts for external operations:

async function fetchWithTimeout(url, timeoutMs = 5000) {
  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), timeoutMs);
  
  try {
    const response = await fetch(url, { 
      signal: controller.signal 
    });
    clearTimeout(timeoutId);
    return response;
  } catch (error) {
    clearTimeout(timeoutId);
    if (error.name === 'AbortError') {
      throw new Error(`Request timeout after ${timeoutMs}ms`);
    }
    throw error;
  }
}

Graceful Shutdown

Handle shutdown signals properly to avoid data loss:

const activeRequests = new Set();

// Track active operations
app.use((req, res, next) => {
  activeRequests.add(req);
  res.on('finish', () => activeRequests.delete(req));
  next();
});

// Graceful shutdown
async function shutdown() {
  console.log('Shutting down gracefully...');
  
  // Stop accepting new connections
  server.close();
  
  // Wait for active requests to complete (with timeout)
  const timeout = setTimeout(() => {
    console.log('Forcing shutdown after timeout');
    process.exit(1);
  }, 10000);
  
  while (activeRequests.size > 0) {
    await new Promise(resolve => setTimeout(resolve, 100));
  }
  
  clearTimeout(timeout);
  process.exit(0);
}

process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);

Monitoring Event Loop Lag

Monitor event loop health in production:

const { monitorEventLoopDelay } = require('perf_hooks');

const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();

setInterval(() => {
  const lag = histogram.mean / 1e6; // Convert to ms
  console.log(`Event loop lag: ${lag.toFixed(2)}ms`);
  
  if (lag > 50) {
    console.warn('High event loop lag detected!');
  }
  
  histogram.reset();
}, 10000);
Rule of thumb: If event loop lag consistently exceeds 50ms, your application is struggling to keep up with the workload.

6. libuv: The Backbone of Node.js

libuv is a multi-platform support library that provides Node.js with its asynchronous I/O capabilities. It is written in C and acts as an abstraction layer for various operating system mechanisms.

Core Features

  • Event Loop: Implements the event loop, which is central to Node.js's non-blocking I/O model.
  • Thread Pool: Manages a pool of threads for executing tasks that cannot be performed asynchronously, such as file system operations.
  • Asynchronous I/O: Provides cross-platform asynchronous I/O operations.
  • Utilities: Includes utilities for DNS resolution, file system watching, and more.

How libuv Works

libuv uses a combination of the following mechanisms to achieve its functionality:

  • IOCP (Windows): Input/Output Completion Ports for asynchronous I/O.
  • epoll (Linux): A scalable I/O event notification system.
  • kqueue (macOS, FreeBSD): A notification interface for I/O events.

By abstracting these platform-specific mechanisms, libuv ensures that Node.js applications behave consistently across different operating systems.

Fun Fact: The name "libuv" stands for "library for Unix and Windows."

JavaScript: Single-Threaded vs Node.js Multi-Threading

Excellent question — and one that’s often misunderstood.

Short answer:

JavaScript itself is single-threaded, but Node.js (and browsers) provide multi-threaded capabilities under the hood.

Let’s break it down clearly:

1. The JavaScript engine (like V8)
  • Runs on a single thread.
  • Executes one piece of code at a time — this is the main thread.
  • All your synchronous JavaScript runs here: function calls, loops, etc.
console.log("A");
console.log("B");
// Always prints A then B

There’s no true parallelism in JavaScript execution here — the interpreter processes one statement at a time.

⚙️ 2. Node.js and its asynchronous power

Node.js uses the libuv library to manage asynchronous I/O — and this is where multi-threading enters the picture.

When you run asynchronous code like:

fs.readFile('data.txt', 'utf8', (err, data) => {
  console.log("File read complete");
});

Node.js doesn’t read the file on the main thread. Instead, libuv offloads file I/O to a thread pool (usually 4 threads by default). When it’s done, it sends a signal back to the event loop, which executes your callback.

So:

  • JavaScript thread: 1
  • Worker threads (I/O, crypto, etc.): multiple

→ This gives the illusion of multi-threading, while your JavaScript logic remains single-threaded.

3. True multi-threading in Node.js

If you actually want to run JS code in parallel, Node.js offers:

  • Worker Threads API (introduced in Node.js v10.5.0)
const { Worker, isMainThread, parentPort } = require('worker_threads');

if (isMainThread) {
  new Worker(__filename); // spawns a new thread
  console.log("Main thread");
} else {
  console.log("Worker thread");
}

Each worker runs its own JS thread and memory space.
⚠️ Communication happens via messages, not shared memory.

4. In browsers

The story is similar:

  • JavaScript runs on a single thread.
  • But browsers have Web APIs (for timers, fetch, DOM events) running on separate threads.
  • And for true concurrency, we can use Web Workers or SharedArrayBuffer.
