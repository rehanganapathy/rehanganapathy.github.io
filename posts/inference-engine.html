Shipping tokens to you, quicker

An LLM inference engine from scratch, and how it went from 9.6 to 307 tokens a second on an Apple M5

An LLM server built from first principles in about 1,100 lines of Python: a hand-written Qwen3 decoder, a preallocated KV cache, continuous batching, and a FastAPI front end that streams tokens over Server-Sent Events. Same model, same laptop, 32× the throughput.

There is no inference library under this. Every speedup on this page comes from one idea at a time, each fixing the bottleneck the previous version exposed. The naive loop recomputes the whole conversation for every new token. A KV cache stops that. Batching shares each forward pass across many requests. Continuous batching keeps that batch full when requests finish at different times. One more change, switching the Mac default from fp32 to fp16, nearly doubled everything again.

Why the first version is slow

A language model produces one token per forward pass. To pick token n, attention needs keys and values for every token before it. The simplest loop feeds the whole sequence back in each time: prompt plus everything generated so far. It is correct, and it is the reference every faster version is tested against. It also does the same work over and over.

The benchmark below measures exactly that, one request at a time, as the prompt grows. Naive decode speed falls off a cliff. With the cache it barely moves, because each step still processes one position. Only the attention read gets longer.

The model, by hand

Qwen3-0.6B is reimplemented directly instead of imported from transformers. The hyperparameters are frozen in engine/config.py, and module names match the Hugging Face checkpoint so the safetensors load with strict=True and no rename table. That matters later: the parity test compares this model's greedy output against Hugging Face's, token for token.

One forward, three call patterns

The same Qwen3.forward(input_ids, positions, cache, slots) serves the naive loop, prefill and decode. Positions are always passed explicitly. That is what makes a ragged decode batch work: every row carries its own absolute position for RoPE and for the attention mask.

KV cache: a pool of slots

The cache is two tensors, k and v, allocated once at startup with shape [num_layers, num_slots, num_kv_heads, max_len, head_dim]. A request owns one slot for its whole life and writes K/V for position p at index p. There is no paging and no sharing between requests. The interesting part is what happens when a request in the middle of the batch finishes.

  • write is one advanced-index put per tensor per layer: k[layer][(slots[:,None], :, positions)] = k.transpose(1, 2).
  • read returns [B, kv_heads, kv_len, head_dim] plus a boolean mask where key j is visible to query i when j ≤ positions[b, i]. That one rule is both the causal mask inside a prefill and the padding mask across a ragged decode batch.
  • move copies only seq_len − 1 positions. The newest token's K/V does not exist yet; the next decode writes it.
  • release never clears the slot. Stale data is harmless because the mask hides every position past a sequence's own length, and test_cache_slot_reuse_is_clean checks exactly that.

How big is the pool?

Per token, every layer stores one K and one V vector per KV head: 2 × 28 × 8 × 128 = 57,344 numbers. The pool reserves that for max_len positions in every slot, whether or not a request ever uses them.

With the server defaults (MAX_BATCH=32, MAX_LEN=2048) the pool is 7.0 GiB in fp16, more than six times the size of the model's weights. Until recently the Mac default was fp32, which doubled it to 14 GiB before a single request arrived. The median request in the benchmark trace (279 prompt + 128 output tokens) fills about a fifth of its slot. That reserved, idle space is exactly what paged attention, planned for a later phase, removes.

Scheduling: static vs continuous

A batch of one wastes most of the GPU, because decode is limited by reading weights from memory, and every request in a batch shares that read. So the scheduler runs one forward pass for all running requests at once. Requests move through three collections: a waiting deque, a running list and a finished list. All of the batching behaviour lives in one method, and the order of its four calls matters.

def step(self) -> StepStats:
    n_running = len(self.running)
    tokens = 0
    if self.running:
        tokens += self._decode(self.running)   # one [B, 1] forward for every running request
        self._retire()                         # free slots of anything that hit EOS / max_tokens
    admitted = self._admit()                   # fill free slots, prefill each admission
    tokens += admitted
    self._retire()                             # an admission can finish on its first token
    ...

The whole difference is one branch

The static baseline is not separate code. _admit starts with if self.mode == "static" and self.running: return 0. In static mode nothing joins until the whole batch has drained, so slots freed by short requests sit idle while the longest one finishes. In continuous mode a freed slot is refilled on the same step. Both modes share everything else, so any benchmark difference between them is the admission policy alone.

Two things are deliberately missing, and the docstring says so. There is no preemption: an admitted request runs to completion. There is no chunked prefill: an admission's entire prompt is processed inside the step, so every running request waits for it. The benchmarks show what that second one costs.

Life of a request

Follow one streamed chat request from the HTTP body to the last SSE event. Three execution contexts share the work: the asyncio event loop, a 4-thread tokenizer pool, and a single step thread that owns the model and the KV cache. The design goal is simple. The event loop must never block on the GPU, and the GPU must never wait on Python string handling.

The step pool has exactly one worker, so the model and cache are only ever touched by one thread and need no locking. The only structure shared across threads is the waiting deque, guarded by sched.lock.

The fp32 default that cost half the throughput

For most of this project the engine ran in fp32 on the Mac. The reason was one line in engine/config.py: bf16 on CUDA, fp32 everywhere else, "where bf16 kernels are slow or missing." That was a reasonable guess for older MPS builds. It had never been measured on this machine.

Measuring it took one short script: the same 200-token prompt, 128 greedy tokens, one model load per dtype.

dtypetok/s, 1 requesttok/s, batch of 16weights + 16×1k KVmatches fp32 greedy
fp3234.13386.1 GBreference
fp1642.96293.1 GB128 of 128 tokens
bf1643.06313.1 GBdiverges at token 16

Half precision was 1.9× faster in a batch and used half the memory. The fallback was the slow path.

Both half-precision formats run at the same speed on the M5, so the choice came down to numerics. bf16 keeps fp32's range but only 8 bits of mantissa, so near-ties between two candidate tokens flip and the text drifts from fp32 after a few words. The output is not worse, just different. fp16 has 11 bits of mantissa and tracked fp32 exactly for all 128 tokens. Its risk is the other direction: a maximum of about 65,504, which a model trained in bf16 could exceed in some activation. Qwen3 normalizes its queries and keys per head, and this code runs RMSNorm in fp32, so that never happened here. If it ever does, DTYPE=bf16 is the switch.

def pick_dtype(device, name=None):
    if name:
        return {"bf16": torch.bfloat16, "fp16": torch.float16, "fp32": torch.float32}[name]
    return {"cuda": torch.bfloat16, "mps": torch.float16}.get(device.type, torch.float32)
engine/config.py · pick_dtype

The new default halves the KV pool from 14 GiB to 7 GiB and brings the batched numbers below with it. On the trace, continuous batching at concurrency 4 went from 34.4 tok/s in the old fp32 run (first 12 requests) to 140.9 tok/s (first 64). That jump is larger than precision alone explains. The request mix differs, and the machine moved from macOS 26.6 to 27.0 between the two runs. The table above is the controlled comparison. The correctness tests still run in fp32 on purpose: they compare token ids exactly, and exact comparisons need exact arithmetic.

Benchmarks

The harness came first, before any optimization, so every number is comparable. It drives a scheduler in-process with no HTTP in the loop and timestamps every generated token. Runs are closed-loop: c requests stay in flight and each completion triggers the next submission. EOS is ignored so the trace's output lengths are what gets measured. Two warm-up requests run first so kernel compilation is not billed to request 0.

The trace (make_trace.py, seed 1234) draws requests from log-normal distributions: prompts with median 279 tokens (22 to 1,024), outputs with median 128 (21 to 512). Same-length requests would hide the entire benefit of continuous batching, because they would all finish together.

Continuous batching beats static at every concurrency above 1, by 1.85× at 4 slots, 1.64× at 16 and 1.30× at 32. At concurrency 1 the two modes are the same algorithm and land on the same 44.6 tok/s. At 32 slots the 64-request run is only two static batches deep, so that point says less about the gap than the others. Against the naive loop, which serves one request at a time at 9.6 tok/s, continuous batching at 32 slots is 32× faster on the same machine.

The bigger difference is latency. At 16 slots a static request waits a median 8.2 s for its first token, because it cannot join until the whole batch drains. Continuous admits it on the next step, in 134 ms. Static's median dips at 32 slots only because half of the 64 requests sit in the first batch and start at once. The price shows up in time per output token: 48 ms against static's 41 at 16 slots, and 79 against 65 at 32. Every admission's prefill runs inside a step, and every running stream waits for it. That is the chunked-prefill item on the deferred list.

Correctness gates

Every gate compares token ids, not text. A broken KV cache usually produces fluent, plausible output that is simply different, so "looks fine" catches nothing. An off-by-one RoPE position reads like a model having a slightly odd day.

Sharp edges and what comes next

  • Prefill stalls decode. Admission prefills the full prompt inside step(), so a 1,024-token prompt holds every running stream for that whole pass. It shows up as continuous batching's higher time per output token. Chunked prefill is the fix.
  • Stop does not stop the GPU. The chat page's Stop button closes the stream, but the scheduler has no cancellation, so the request keeps generating until max_tokens. A disconnect hook that marks the request finished is a small change.
  • Reserved, idle cache. Every slot holds MAX_LEN positions, 7 GiB at the defaults. Paged attention and prefix caching are the next-phase fixes.
  • No back-pressure. The waiting deque is unbounded and there is no preemption; a long request holds its slot until it finishes.
  • Static refills one step late. The harness submits replacements only after step() returns, so a static batch restarts with one slot short. It slightly understates static throughput.
  • Provenance. Result files record git: null, because the machine's git binary could not run when they were produced.

Explicitly out of scope for phase 1, per phase-1-plan.md: paged attention, prefix caching, chunked prefill, preemption, quantization, CUDA graphs, Triton kernels, tensor parallelism and Prometheus metrics.
